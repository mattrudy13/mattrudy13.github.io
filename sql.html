Top N per group

The top two customers by revenue in each region. A window function numbers the rows inside each region, and the outer query keeps the first N.

sales
regioncustomerrevenue
EastAcme900
EastBirch650
EastCobalt650
EastDune300
WestEmber1200
WestFjord480
WestGrove220
 
WITH ranked AS (
  SELECT
    region,
    customer,
    revenue,
    ROW_NUMBER() OVER (
      PARTITION BY region
      ORDER BY revenue DESC, customer
    ) AS rn
  FROM sales
)
SELECT region, customer, revenue
FROM ranked
WHERE rn <= 2

Result

regioncustomerrevenue
EastAcme900
EastBirch650
WestEmber1200
WestFjord480

Ties: Birch and Cobalt both have 650. ROW_NUMBER always returns exactly N rows, so the tiebreaker (customer) decides who makes it. To keep every tied row, use RANK() instead: East would return Acme, Birch and Cobalt. Without a tiebreaker, ROW_NUMBER can pick a different row on each run.

Removing duplicates

Keep one row per customer: the most recently updated. Same window-function idea, numbered newest first, keeping row 1.

WITH ranked AS (
  SELECT
    customer_id,
    email,
    updated_at,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY updated_at DESC
    ) AS rn
  FROM customer_raw
)
SELECT customer_id, email, updated_at
FROM ranked
WHERE rn = 1

Result

Why not DISTINCT: SELECT DISTINCT only removes rows that match in every column. It drops customer 3's exact copy but keeps both of customer 1's rows, because the emails differ. Databricks also accepts QUALIFY ROW_NUMBER() OVER (...) = 1 as a shorter way to write the same filter.

Running totals and moving averages

A total that adds up day by day, and a three-day moving average. Both are window functions with a frame: which rows around the current one to include.

daily_sales
dayamount
2026-03-01100
2026-03-02140
2026-03-0380
2026-03-04160
2026-03-05120
2026-03-06200
2026-03-0790
 
SELECT
  day,
  amount,
  SUM(amount) OVER (
    ORDER BY day
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total,
  ROUND(AVG(amount) OVER (
    ORDER BY day
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
  ), 1) AS avg_3day
FROM daily_sales

Watch the frame: the first two averages cover fewer than three days (100 is just day 1). The frame counts rows, not days, so a missing day silently stretches the window; fill the gaps first. Spelling out ROWS also matters for the running total: with only ORDER BY, the default frame is RANGE, which gives tied days the same total.

Period over period

Each month's revenue next to the month before, with the change and the percent change. LAG reads a value from the previous row.

monthly_revenue
monthrevenue
2026-01400
2026-02460
2026-03414
2026-04500
 
WITH with_prev AS (
  SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_revenue
  FROM monthly_revenue
)
SELECT
  month,
  revenue,
  prev_revenue,
  revenue - prev_revenue AS change,
  ROUND(100 * (revenue - prev_revenue) / prev_revenue, 1) AS pct_change
FROM with_prev

Previous row, not previous month: if a month is missing, LAG compares against the one before it, so fill gaps first. Computing prev_revenue once in a CTE keeps the math readable. For year over year on monthly data, use LAG(revenue, 12), again only with no missing months.

Gaps and islands

Find each user's streaks of consecutive login days. Subtract a running row number from each date: within a streak, date and row number rise together, so the result stays the same and marks the group.

22026-03-07
 
WITH days AS (
  SELECT DISTINCT user_id, login_date
  FROM logins
),
grouped AS (
  SELECT
    user_id,
    login_date,
    date_sub(
      login_date,
      ROW_NUMBER() OVER (
        PARTITION BY user_id
        ORDER BY login_date
      )
    ) AS streak_id
  FROM days
)
SELECT
  user_id,
  MIN(login_date) AS streak_start,
  MAX(login_date) AS streak_end,
  COUNT(*) AS days
FROM grouped
GROUP BY user_id, streak_id
ORDER BY user_id, streak_start

The DISTINCT matters: user 1 logged in twice on March 2. Without removing that duplicate, the row numbers run ahead of the dates and user 1's streaks come out wrong: 4 days from March 1 to 6, and 2 more from March 2 to 3.

Upserts with Delta MERGE

Apply a batch of changes to a Delta table in one statement: update customers that exist, insert the ones that don't.

customers (target)
customer_idemailupdated_at
1ana@old.com2026-01-04
2ben@mail.com2026-01-15
customer_updates (source)
customer_idemailupdated_at
1ana@new.com2026-02-10
3cy@mail.com2026-01-20
 
MERGE INTO customers AS t
USING customer_updates AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED THEN
  UPDATE SET
    t.email = s.email,
    t.updated_at = s.updated_at
WHEN NOT MATCHED THEN
  INSERT (customer_id, email, updated_at)
  VALUES (s.customer_id, s.email, s.updated_at)

One source row per key: if two source rows match the same target row, the merge fails instead of guessing which one wins. Deduplicate the source first with the pattern above. When the columns line up, UPDATE SET * and INSERT * save listing them.

Keeping history with MERGE (SCD Type 2)

Instead of overwriting a changed email, close the old row and add a new one, so the table keeps every version with the dates it was true. The trick is to stage each changed customer twice: once to close its current row, and once with a NULL key so it can't match anything and gets inserted.

customer_history (target)
customer_idemailvalid_fromvalid_tois_current
1ana@old.com2026-01-04NULLtrue
2ben@mail.com2026-01-15NULLtrue
customer_updates (source)
customer_idemailupdated_at
1ana@new.com2026-02-10
2ben@mail.com2026-02-10
3cy@mail.com2026-02-10
 
CREATE OR REPLACE TEMP VIEW staged_updates AS
WITH changed AS (
  SELECT s.*
  FROM customer_updates AS s
  JOIN customer_history AS t
    ON s.customer_id = t.customer_id
   AND t.is_current
   AND NOT (s.email <=> t.email)
)
SELECT customer_id AS merge_key, * FROM customer_updates
UNION ALL
SELECT NULL AS merge_key, * FROM changed;

MERGE INTO customer_history AS t
USING staged_updates AS s
  ON t.customer_id = s.merge_key
 AND t.is_current
WHEN MATCHED AND NOT (t.email <=> s.email) THEN
  UPDATE SET
    t.valid_to = s.updated_at,
    t.is_current = false
WHEN NOT MATCHED THEN
  INSERT (customer_id, email, valid_from, valid_to, is_current)
  VALUES (s.customer_id, s.email, s.updated_at, NULL, true);

How each row lands: customer 1 changed, so its current row is closed and its NULL-key copy is inserted as the new current row. Customer 2 matches but hasn't changed, so neither clause fires. Customer 3 is new and gets inserted. <=> is the null-safe equals: with plain <>, a change to or from NULL would be missed. Track more columns by adding them to both comparisons.

Filling date gaps

Daily totals with a row for every day, including days with no orders. Build a calendar of dates, then left join the data onto it.

orders
order_dateamount
2026-03-01120
2026-03-0180
2026-03-0245
2026-03-04210
2026-03-0660
2026-03-0615
 
WITH days AS (
  SELECT explode(sequence(
    DATE'2026-03-01',
    DATE'2026-03-07',
    INTERVAL 1 DAY
  )) AS day
),
daily AS (
  SELECT order_date AS day, SUM(amount) AS amount
  FROM orders
  GROUP BY order_date
)
SELECT d.day, COALESCE(a.amount, 0) AS amount
FROM days AS d
LEFT JOIN daily AS a
  ON a.day = d.day
ORDER BY d.day

Keep the COALESCE: without it, empty days come back as NULL, and an average over the result skips them instead of counting them as zero. Here the daily average is 530 ÷ 7 = 75.7 with zeros, but 530 ÷ 4 = 132.5 with nulls.
